# Машинный API: `--json` для скриптов и GUI

[← README](../../README.ru.md) · [English](../machine-api.md)

У пяти команд — `list`, `doctor`, `status`, `links`, `usage` — есть режим
`--json`, предназначенный для разбора скриптом или другой программой, а не
для чтения человеком. Это контракт, на который опирается, например,
GUI-клиент.

## Правила, общие для каждой `--json`-команды

- **Ровно один JSON-документ в stdout, и ничего больше.** Никакой подсказки
  об обновлении, никакого прогресса, никакого декоративного текста.
  Если потребитель видит в stdout что-то ещё, весь вызов нужно считать
  неудачным, а не пытаться найти JSON среди шума.
- **`schema_version`** — целое число, отдельное для каждой команды, начиная
  с `1`. Новый релиз может добавить поля без увеличения версии; она растёт
  только когда меняется *смысл* существующего поля или поле удаляется.
- **`ok: true`** означает, что результирующий документ был построен — а не
  что всё описанное в нём здорово. Самый наглядный пример — `doctor
  --json`: `ok: true` может стоять рядом с аккаунтом `offline` и ненулевым
  кодом выхода (см. ниже).
- **Операционные ошибки** — например, нечитаемое собственное хранилище
  конфигурации claude-acc — единственный случай, когда возвращается
  конверт ошибки:
  ```json
  {
    "schema_version": 1,
    "ok": false,
    "error": { "code": "SOME_STABLE_CODE", "message": "для человека, не для разбора", "details": {} }
  }
  ```
  Логика ветвления должна смотреть на `error.code`, никогда на `message` —
  `message` может отличаться между значениями `CLAUDE_ACC_LANG` или
  версиями; `code` — нет.
- **Ни одно поле не несёт секрет** — ни токен, ни хеш, ни содержимое файла
  с учётными данными.
- Пути абсолютные. Поддерживаемые платформы используют свой нативный
  разделитель (`\` в Windows, `/` в остальных случаях); для отображения
  ничего не переписывается.
- **Эквивалентность путей зависит от платформы, и только у Windows она
  нечувствительна к регистру/разделителю.** В Windows claude-acc считает
  регистр и `/` против `\` эквивалентными при сравнении сохранённых
  привязок (`src/path_identity.rs`). На любой другой поддерживаемой
  платформе эквивалентность путей — точное совпадение строк:
  `/Users/alice/work` и `/Users/alice/Work` там — два разных,
  непротиворечащих друг другу пути, а не неоднозначность. Примеры ниже
  используют повторяющиеся, одинаково написанные сохранённые пути именно
  поэтому — чтобы они были верны независимо от платформы.

## `claude-acc list --json`

Быстро, локально, без сети — безопасно вызывать при каждом запуске GUI.
Каждое поле берётся из уже имеющихся на диске данных.

```bash
$ claude-acc list --json
{
  "schema_version": 1,
  "ok": true,
  "accounts": [
    {
      "name": "work",
      "managed": true,
      "default": true,
      "auth_present": true,
      "cached_email": "alice@anthropic.com",
      "cached_uuid": "aa6c22d5-...",
      "cached_plan": "Max 20x",
      "token_changed_since_audit": false,
      "chrome_enabled": true,
      "config_dir": "/Users/alice/.claude-switch/accounts/work"
    },
    {
      "name": "default",
      "managed": false,
      "default": false,
      "auth_present": false,
      "cached_email": null,
      "cached_uuid": null,
      "cached_plan": null,
      "token_changed_since_audit": false,
      "chrome_enabled": null,
      "config_dir": "/Users/alice/.claude"
    }
  ]
}
```

- Стандартный, неуправляемый аккаунт `~/.claude/` — когда он присутствует —
  всегда представлен стабильным именем `"default"` с `"managed": false`.
  Он появляется только после того, как им действительно воспользовались
  (настоящий логин или существующий кеш `doctor`) — то же правило
  видимости, что и у человекочитаемого `list`.
- `auth_present` — это только локальная проверка наличия токена, без
  сетевого запроса. Это *не* то же самое, что "кеш идентичности свежий":
  у аккаунта может быть `auth_present: true` при пустом `cached_email`,
  если `doctor` его ещё не аудировал.
- `token_changed_since_audit` означает, что токен OAuth на диске больше не
  совпадает с тем, что последним закешировал `doctor` — обычно это
  обычное обновление токена, а не само по себе суждение о личности (это
  работа `doctor`).
- `chrome_enabled` — это `true`/`false`/`null` — `null` означает, что этому
  конфиг-каталогу никогда не предлагали Claude в Chrome, а не "выключено".
- Ошибка: `CONFIG_STORE_UNREADABLE`, если сам список аккаунтов не удалось
  перечислить.

## `claude-acc doctor --json`

Орган аудита личности/пина — медленнее, чем `list`, так как обращается
к API профиля OAuth вживую. Добавка к уже существующей форме (`doctor
--json` появился раньше этого контракта): новые — `schema_version`, `ok` и
построчные `chrome_enabled`/`config_dir`; `accounts`/`standard` и их поля
`status`/`email`/`uuid`/`plan`/`lock`/`pinned_uuid` не изменились.

```bash
$ claude-acc doctor --json
{
  "schema_version": 1,
  "ok": true,
  "accounts": [
    {
      "name": "work",
      "status": "ok",
      "email": "alice@anthropic.com",
      "uuid": "aa6c22d5-...",
      "plan": "Max 20x",
      "default": true,
      "lock": "ok",
      "pinned_uuid": "aa6c22d5-...",
      "chrome_enabled": true,
      "config_dir": "/Users/alice/.claude-switch/accounts/work"
    }
  ],
  "standard": null
}
```

**Код выхода сохраняет своё прежнее, отдельное значение** — это не сигнал
операционной ошибки. `claude-acc doctor --json` завершается ненулевым
кодом, когда у какого-то аккаунта `"status": "offline"` или `"lock":
"drift"`; один `"no_token"` — никогда. Корректный документ выводится
всегда первым, так что вызывающая сторона должна разбирать stdout
независимо от кода выхода — ненулевой код тут означает "аудированный
аккаунт требует внимания", а не "claude-acc не смог построить результат".

## `claude-acc status --json [--path <dir>]`

Единственный авторитетный ответ на вопрос "какой аккаунт `claude`
реально выберет для этой директории прямо сейчас". Никогда не
переизобретайте эту логику сами — вызывайте эту команду с нужной
директорией, через текущий cwd или через `--path` (`--path` требует
`--json`).

```bash
$ claude-acc status --json
{
  "schema_version": 1,
  "ok": true,
  "query_path": "/Users/alice/work/project-a",
  "resolved_account": "work",
  "source": "linked",
  "owning_link_path": "/Users/alice/work"
}
```

- `source` — одно из: `"linked"` (совпала привязка одной из родительских
  директорий — см. `owning_link_path`, какая именно), `"default"` (привязки
  нет, применяется настроенный управляемый аккаунт по умолчанию) или
  `"standard"` (нет ни привязки, ни управляемого аккаунта по умолчанию).
- Стандартный аккаунт — это `resolved_account: "default"`, никогда
  `null` — тот же стабильный идентификатор, что использует `list --json`,
  так что поле реестра проекта можно сравнивать с этим значением напрямую,
  без отдельной обработки `null`.
- Поля `ambiguous` не существует. У неоднозначности (две и более
  эквивалентные привязки, указывающие на разные аккаунты) есть ровно одно
  представление — конверт ошибки:
  ```json
  {
    "schema_version": 1,
    "ok": false,
    "error": {
      "code": "AMBIGUOUS_LINK",
      "message": "...",
      "details": {
        "query_path": "/Users/alice/Work",
        "mappings": [
          { "stored_path": "/Users/alice/Work", "account": "personal1" },
          { "stored_path": "/Users/alice/Work", "account": "personal2" }
        ]
      }
    }
  }
  ```
  (Две *одинаково написанные* сохранённые привязки, указывающие на разные
  аккаунты — самая простая неоднозначность, верная на любой платформе. В
  Windows два варианта написания одной директории, отличающиеся регистром
  или разделителем, конфликтовали бы так же; на других платформах — нет,
  так как эквивалентность путей там точная по строке — см. примечание
  выше.)
- Ошибки `--path`: `PATH_NOT_FOUND`, если пути не существует,
  `PATH_NOT_DIRECTORY`, если он существует, но не является директорией.

## `claude-acc links --json`

Сохранённая карта директория→аккаунт плюс полноценный анализ конфликтов
по всему хранилищу — никогда путь для изменения.

```bash
$ claude-acc links --json
{
  "schema_version": 1,
  "ok": true,
  "links": [
    { "stored_path": "/Users/alice/work", "account": "personal1" },
    { "stored_path": "/Users/alice/work", "account": "personal2" }
  ],
  "conflicts": [
    {
      "code": "AMBIGUOUS_EQUIVALENT_PATHS",
      "mappings": [
        { "stored_path": "/Users/alice/work", "account": "personal1" },
        { "stored_path": "/Users/alice/work", "account": "personal2" }
      ]
    }
  ]
}
```

- `links` — это полный, безусловный дамп в порядке хранения — исходное
  написание (регистр, разделители, каждый символ пути и имени аккаунта),
  никогда не нормализуется для отображения. Единственное исключение — не
  нормализация, а синтаксис самого формата хранения: пробелы,
  непосредственно прилегающие к разделителю `=`, обрезаются при разборе
  строки — так же, как для любого файла вида `ключ=значение`. Строка,
  записанная как `  /Users/alice/work  =personal1`, сохраняет
  `/Users/alice/work`, а не копию с этими пробелами. Это не побайтовое
  сохранение строки целиком; это сохранение написания именно тех значений
  пути и аккаунта, которые разделяет разделитель.
- Группа в `conflicts` появляется только когда два и более *разных*
  аккаунта делят один класс эквивалентности; один и тот же аккаунт,
  привязанный под двумя эквивалентными написаниями, — это ничем не
  примечательные обычные записи `links`. Ни один участник никогда не
  отбрасывается и не выбирается "каноническим".
- В отличие от человекочитаемой команды `links` (которая молча
  пропускает строку, которую не может разобрать), `--json` сообщает об
  этом: `LINKS_STORE_INVALID`, с `details.lines: [{line_number, raw}, ...]`
  для каждой проблемной строки, вместо того чтобы тихо вернуть неполную
  карту, как если бы она была полной. `LINKS_STORE_UNREADABLE` покрывает
  сбой на уровне файловой системы.

## `claude-acc usage --json`

Только информационно — утилизация и временные метки сброса, никогда план
(он принадлежит `cached_plan` из `list --json` / `plan` из `doctor
--json`). Никогда ничего не блокирует; медленный или неудачный запрос
превращается в `"unavailable"`.

```bash
$ claude-acc usage --json
{
  "schema_version": 1,
  "ok": true,
  "accounts": [
    {
      "name": "work",
      "source": "live",
      "fetched_at": "2026-10-05T12:00:00Z",
      "five_hour": { "utilization": 42, "resets_at": "2026-10-05T14:14:00Z" },
      "seven_day": { "utilization": 11, "resets_at": "2026-10-10T00:00:00Z" }
    },
    {
      "name": "personal",
      "source": "unavailable",
      "fetched_at": null,
      "five_hour": null,
      "seven_day": null
    }
  ]
}
```

- `source: "live"` — получено в этом вызове. `"cache"` — живой запрос не
  удался, поэтому использовано собственное последнее показание Claude
  Code (отклоняется, если принадлежит не той личности, что сейчас вошла в
  систему). `"unavailable"` — не сработало ни то, ни другое.
- Закешированное окно, чей `resets_at` уже прошёл, — это `null`, а не
  показ как актуального — то же подавление, что применяет к устаревшему
  показанию человекочитаемая команда `usage`. *Живое* показание так
  никогда не подавляется.
- Видимость аккаунтов та же, что у `list --json`: стандартный аккаунт
  появляется только после того, как им действительно воспользовались.

## Версионирование

`schema_version` — отдельная для каждой команды величина, начинающаяся с
`1`. Потребитель должен отказываться работать с `schema_version` ниже
требуемой ("claude-acc нужно обновить") и отказываться работать с более
высокой, чем он понимает ("claude-acc новее, чем ожидает эта сборка") —
никогда не разбирать её тихо "как получится" в любую сторону.
