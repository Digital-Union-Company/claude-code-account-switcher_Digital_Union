# Машинный API: `--json` для скриптов и GUI

[← README](../../README.ru.md) · [English](../machine-api.md)

У шести команд есть режим `--json`, предназначенный для разбора скриптом или
другой программой, а не для чтения человеком. Пять из них — `list`, `doctor`,
`status`, `links`, `usage` — только читают, а одна, `link --json`, — это
единственная мутация машинного API: она условно записывает одну привязку
директория→аккаунт. Это контракт, на который опирается, например, GUI-клиент.

## Правила, общие для каждой `--json`-команды

- **Ровно один JSON-документ в stdout, и ничего больше.** Никакой подсказки
  об обновлении, никакого прогресса, никакого декоративного текста.
  Если потребитель видит в stdout что-то ещё, весь вызов нужно считать
  неудачным, а не пытаться найти JSON среди шума.
- **`schema_version`** — целое число, отдельное для каждой команды, начиная
  с `1`. Новый релиз может добавить поля без увеличения версии; она растёт
  только когда меняется *смысл* существующего поля или поле удаляется.
- **`ok: true`** означает, что результирующий документ был построен — а не
  что всё описанное в нём здорово. Самый наглядный пример — `doctor
  --json`: `ok: true` может стоять рядом с аккаунтом `offline` и ненулевым
  кодом выхода (см. ниже).
- **Операционные ошибки** — например, нечитаемое собственное хранилище
  конфигурации claude-acc — единственный случай, когда возвращается
  конверт ошибки:
  ```json
  {
    "schema_version": 1,
    "ok": false,
    "error": { "code": "SOME_STABLE_CODE", "message": "для человека, не для разбора", "details": {} }
  }
  ```
  Логика ветвления должна смотреть на `error.code`, никогда на `message` —
  `message` может отличаться между значениями `CLAUDE_ACC_LANG` или
  версиями; `code` — нет.
- **Ни одно поле не несёт секрет** — ни токен, ни хеш, ни содержимое файла
  с учётными данными.
- Пути абсолютные. Поддерживаемые платформы используют свой нативный
  разделитель (`\` в Windows, `/` в остальных случаях); для отображения
  ничего не переписывается.
- **Эквивалентность путей зависит от платформы, и только у Windows она
  нечувствительна к регистру/разделителю.** В Windows claude-acc считает
  регистр и `/` против `\` эквивалентными при сравнении сохранённых
  привязок (`src/path_identity.rs`). На любой другой поддерживаемой
  платформе эквивалентность путей — точное совпадение строк:
  `/Users/alice/work` и `/Users/alice/Work` там — два разных,
  непротиворечащих друг другу пути, а не неоднозначность. Примеры ниже
  используют повторяющиеся, одинаково написанные сохранённые пути именно
  поэтому — чтобы они были верны независимо от платформы.

## `claude-acc list --json`

Быстро, локально, без сети — безопасно вызывать при каждом запуске GUI.
Каждое поле берётся из уже имеющихся на диске данных.

```bash
$ claude-acc list --json
{
  "schema_version": 1,
  "ok": true,
  "accounts": [
    {
      "name": "work",
      "managed": true,
      "default": true,
      "auth_present": true,
      "cached_email": "alice@anthropic.com",
      "cached_uuid": "aa6c22d5-...",
      "cached_plan": "Max 20x",
      "token_changed_since_audit": false,
      "chrome_enabled": true,
      "config_dir": "/Users/alice/.claude-switch/accounts/work"
    },
    {
      "name": "default",
      "managed": false,
      "default": false,
      "auth_present": false,
      "cached_email": null,
      "cached_uuid": null,
      "cached_plan": null,
      "token_changed_since_audit": false,
      "chrome_enabled": null,
      "config_dir": "/Users/alice/.claude"
    }
  ]
}
```

- Стандартный, неуправляемый аккаунт `~/.claude/` — когда он присутствует —
  всегда представлен стабильным именем `"default"` с `"managed": false`.
  Он появляется только после того, как им действительно воспользовались
  (настоящий логин или существующий кеш `doctor`) — то же правило
  видимости, что и у человекочитаемого `list`.
- `auth_present` — это только локальная проверка наличия токена, без
  сетевого запроса. Это *не* то же самое, что "кеш идентичности свежий":
  у аккаунта может быть `auth_present: true` при пустом `cached_email`,
  если `doctor` его ещё не аудировал.
- `token_changed_since_audit` означает, что токен OAuth на диске больше не
  совпадает с тем, что последним закешировал `doctor` — обычно это
  обычное обновление токена, а не само по себе суждение о личности (это
  работа `doctor`).
- `chrome_enabled` — это `true`/`false`/`null` — `null` означает, что этому
  конфиг-каталогу никогда не предлагали Claude в Chrome, а не "выключено".
- Ошибка: `CONFIG_STORE_UNREADABLE`, если сам список аккаунтов не удалось
  перечислить.

## `claude-acc doctor --json`

Орган аудита личности/пина — медленнее, чем `list`, так как обращается
к API профиля OAuth вживую. Добавка к уже существующей форме (`doctor
--json` появился раньше этого контракта): новые — `schema_version`, `ok` и
построчные `chrome_enabled`/`config_dir`; `accounts`/`standard` и их поля
`status`/`email`/`uuid`/`plan`/`lock`/`pinned_uuid` не изменились.

```bash
$ claude-acc doctor --json
{
  "schema_version": 1,
  "ok": true,
  "accounts": [
    {
      "name": "work",
      "status": "ok",
      "email": "alice@anthropic.com",
      "uuid": "aa6c22d5-...",
      "plan": "Max 20x",
      "default": true,
      "lock": "ok",
      "pinned_uuid": "aa6c22d5-...",
      "chrome_enabled": true,
      "config_dir": "/Users/alice/.claude-switch/accounts/work"
    }
  ],
  "standard": null
}
```

**Код выхода сохраняет своё прежнее, отдельное значение** — это не сигнал
операционной ошибки. `claude-acc doctor --json` завершается ненулевым
кодом, когда у какого-то аккаунта `"status": "offline"` или `"lock":
"drift"`; один `"no_token"` — никогда. Корректный документ выводится
всегда первым, так что вызывающая сторона должна разбирать stdout
независимо от кода выхода — ненулевой код тут означает "аудированный
аккаунт требует внимания", а не "claude-acc не смог построить результат".

## `claude-acc status --json [--path <dir>]`

Единственный авторитетный ответ на вопрос "какой аккаунт `claude`
реально выберет для этой директории прямо сейчас". Никогда не
переизобретайте эту логику сами — вызывайте эту команду с нужной
директорией, через текущий cwd или через `--path` (`--path` требует
`--json`).

```bash
$ claude-acc status --json
{
  "schema_version": 1,
  "ok": true,
  "query_path": "/Users/alice/work/project-a",
  "resolved_account": "work",
  "source": "linked",
  "owning_link_path": "/Users/alice/work"
}
```

- `source` — одно из: `"linked"` (совпала привязка одной из родительских
  директорий — см. `owning_link_path`, какая именно), `"default"` (привязки
  нет, применяется настроенный управляемый аккаунт по умолчанию) или
  `"standard"` (нет ни привязки, ни управляемого аккаунта по умолчанию).
- Стандартный аккаунт — это `resolved_account: "default"`, никогда
  `null` — тот же стабильный идентификатор, что использует `list --json`,
  так что поле реестра проекта можно сравнивать с этим значением напрямую,
  без отдельной обработки `null`.
- Поля `ambiguous` не существует. У неоднозначности (две и более
  эквивалентные привязки, указывающие на разные аккаунты) есть ровно одно
  представление — конверт ошибки:
  ```json
  {
    "schema_version": 1,
    "ok": false,
    "error": {
      "code": "AMBIGUOUS_LINK",
      "message": "...",
      "details": {
        "query_path": "/Users/alice/Work",
        "mappings": [
          { "stored_path": "/Users/alice/Work", "account": "personal1" },
          { "stored_path": "/Users/alice/Work", "account": "personal2" }
        ]
      }
    }
  }
  ```
  (Две *одинаково написанные* сохранённые привязки, указывающие на разные
  аккаунты — самая простая неоднозначность, верная на любой платформе. В
  Windows два варианта написания одной директории, отличающиеся регистром
  или разделителем, конфликтовали бы так же; на других платформах — нет,
  так как эквивалентность путей там точная по строке — см. примечание
  выше.)
- Ошибки `--path`: `PATH_NOT_FOUND`, если пути не существует,
  `PATH_NOT_DIRECTORY`, если он существует, но не является директорией.

## `claude-acc links --json`

Сохранённая карта директория→аккаунт плюс полноценный анализ конфликтов
по всему хранилищу — никогда путь для изменения.

```bash
$ claude-acc links --json
{
  "schema_version": 1,
  "ok": true,
  "links": [
    { "stored_path": "/Users/alice/work", "account": "personal1" },
    { "stored_path": "/Users/alice/work", "account": "personal2" }
  ],
  "conflicts": [
    {
      "code": "AMBIGUOUS_EQUIVALENT_PATHS",
      "mappings": [
        { "stored_path": "/Users/alice/work", "account": "personal1" },
        { "stored_path": "/Users/alice/work", "account": "personal2" }
      ]
    }
  ]
}
```

- `links` — это полный, безусловный дамп в порядке хранения — исходное
  написание (регистр, разделители, каждый символ пути и имени аккаунта),
  никогда не нормализуется для отображения. Единственное исключение — не
  нормализация, а синтаксис самого формата хранения: пробелы,
  непосредственно прилегающие к разделителю `=`, обрезаются при разборе
  строки — так же, как для любого файла вида `ключ=значение`. Строка,
  записанная как `  /Users/alice/work  =personal1`, сохраняет
  `/Users/alice/work`, а не копию с этими пробелами. Это не побайтовое
  сохранение строки целиком; это сохранение написания именно тех значений
  пути и аккаунта, которые разделяет разделитель.
- Группа в `conflicts` появляется только когда два и более *разных*
  аккаунта делят один класс эквивалентности; один и тот же аккаунт,
  привязанный под двумя эквивалентными написаниями, — это ничем не
  примечательные обычные записи `links`. Ни один участник никогда не
  отбрасывается и не выбирается "каноническим".
- В отличие от человекочитаемой команды `links` (которая молча
  пропускает строку, которую не может разобрать), `--json` сообщает об
  этом: `LINKS_STORE_INVALID`, с `details.lines: [{line_number, raw}, ...]`
  для каждой проблемной строки, вместо того чтобы тихо вернуть неполную
  карту, как если бы она была полной. `LINKS_STORE_UNREADABLE` покрывает
  сбой на уровне файловой системы.

## `claude-acc usage --json`

Только информационно — утилизация и временные метки сброса, никогда план
(он принадлежит `cached_plan` из `list --json` / `plan` из `doctor
--json`). Никогда ничего не блокирует; медленный или неудачный запрос
превращается в `"unavailable"`.

```bash
$ claude-acc usage --json
{
  "schema_version": 1,
  "ok": true,
  "accounts": [
    {
      "name": "work",
      "source": "live",
      "fetched_at": "2026-10-05T12:00:00Z",
      "five_hour": { "utilization": 42, "resets_at": "2026-10-05T14:14:00Z" },
      "seven_day": { "utilization": 11, "resets_at": "2026-10-10T00:00:00Z" }
    },
    {
      "name": "personal",
      "source": "unavailable",
      "fetched_at": null,
      "five_hour": null,
      "seven_day": null
    }
  ]
}
```

- `source: "live"` — получено в этом вызове. `"cache"` — живой запрос не
  удался, поэтому использовано собственное последнее показание Claude
  Code (отклоняется, если принадлежит не той личности, что сейчас вошла в
  систему). `"unavailable"` — не сработало ни то, ни другое.
- Закешированное окно, чей `resets_at` уже прошёл, — это `null`, а не
  показ как актуального — то же подавление, что применяет к устаревшему
  показанию человекочитаемая команда `usage`. *Живое* показание так
  никогда не подавляется.
- Видимость аккаунтов та же, что у `list --json`: стандартный аккаунт
  появляется только после того, как им действительно воспользовались.

## `claude-acc link --json --path <DIR> --account <ACCOUNT>`

**Единственная мутация** машинного API: она делает так, что собственная точная
привязка каталога `<DIR>` указывает на `<ACCOUNT>`, после чего `status --json`
для `<DIR>` разрешается в `<ACCOUNT>` по его собственной точной привязке.
Сделана для GUI, который хочет применить аккаунт из своего реестра к
маршрутизации claude-acc одной условной записью — а не последовательностью
`unlink`-затем-`link`, которую потребитель выполняет сам.

Требуется **ровно один** из двух режимов и обязательно `--path` и `--account`:

- `--dry-run` — разрешить, спланировать и вернуть токен `expected_state`. Ничего
  не пишет.
- `--expect-state <token>` — зафиксировать, но только если состояние
  маршрутизации всё ещё совпадает с этим токеном из предыдущего `--dry-run`.

Таким образом машинная мутация никогда не безусловна: потребитель показывает
предпросмотр, демонстрирует его пользователю и фиксирует изменение против того
состояния, которое пользователь действительно видел.

### Область действия — ровно одна привязка и ничего больше

Команда лишь добавляет, заменяет или оставляет *точно-эквивалентную* привязку
самого `<DIR>`; при изменении она сводит регистровые/слешевые алиасы `<DIR>` к
одной выбранной записи (на Windows), а уже-правильную точную привязку оставляет
байт-в-байт нетронутой. Привязки предков, потомков и не связанные с ними никогда
не затрагиваются. Поскольку маршрутизация наследуется — выигрывает ближайший
привязанный предок — запись точной привязки для `<DIR>` его **закрепляет**:
каталог, который раньше наследовал свой аккаунт, теперь имеет собственную
привязку, и последующее изменение предка его больше не сдвигает. Маршруты
`before`/`after` делают это видимым. Запись точной привязки для `<DIR>` меняет
эффективный аккаунт самого `<DIR>` и любого потомка, наследующего от него, — это
одна *хранимая* привязка, но не обязательно один *эффективный* каталог.

Все решения о маршрутизации и об эквивалентности путей принимает claude-acc
(`src/resolve.rs`, `src/path_identity.rs`); потребитель передаёт каталог и
аккаунт строками и никогда сам не сравнивает пути и не читает файл привязок.

### Предпросмотр — `--dry-run`

```bash
$ claude-acc link --json --path /Users/alice/work/project-a --account work --dry-run
{
  "schema_version": 1,
  "ok": true,
  "dry_run": true,
  "would_change": true,
  "query_path": "/Users/alice/work/project-a",
  "account": "work",
  "before": { "resolved_account": "default", "source": "standard", "owning_link_path": null },
  "after": { "resolved_account": "work", "source": "linked", "owning_link_path": "/Users/alice/work/project-a" },
  "stored_link_path": "/Users/alice/work/project-a",
  "expected_state": "42cfd5972ba543f2f876687273ffc9b737971b0b4589fc342d71cd4b95991f77"
}
```

- `after` — это **проектируемый** маршрут (`dry_run: true` / `would_change`), а
  не утверждение, что что-то записано.
- `expected_state` — это 64-символьный шестнадцатеричный отпечаток всех значимых
  для маршрутизации входных данных: каталога, аккаунта, всего файла привязок,
  настроенного default, списка аккаунтов, **а также самой разрешённой
  интерпретации маршрутизации**: маршрута `before`, который claude-acc разрешает
  для `<DIR>`, полного упорядоченного набора собственных точно-эквивалентных
  хранимых записей `<DIR>` (каждой записи, которую фиксация удалит и заменит, а
  не только первой) и собственной разрешённой идентичности `<DIR>` в файловой
  системе. Это консервативный **отпечаток состояния, а не аутентификация и не
  идентификатор транзакции**: одинаковое восстановленное состояние даёт
  одинаковый токен, поэтому он не отличает "никогда не менялось" от "изменилось и
  вернулось обратно" (изменение типа ABA). Он отказывает при **любом** изменении
  файла привязок, в том числе не связанном с этим каталогом. Он не содержит
  секретов — только строки каталогов, имена аккаунтов и хранимую карту.
- Поскольку разрешённый маршрут, набор точной эквивалентности и идентичность
  каталога берутся из резолвера claude-acc и `path_identity` — которые на
  платформах, где это есть, обращаются к живой идентичности файловой системы
  (`canonicalize`), — смена цели симлинка или junction, меняющая то, как
  интерпретируется `<DIR>`, или то, какие хранимые записи попадают в его класс
  эквивалентности, переворачивает токен и отклоняется на сравнении
  expected-state, даже если ни одна хранимая строка не сдвинулась. Чего токен
  по-прежнему не покрывает — это узкое окно **после** этого сравнения и **до**
  атомарной записи (см. «Атомарность, блокировка и кого она связывает»); там
  гарантию того, что `<DIR>` в итоге разрешается в `<ACCOUNT>` по своей
  собственной точной привязке, даёт перепроверка после записи, а не токен.
- `would_change` равно `false`, когда у `<DIR>` уже есть точная привязка к
  `<ACCOUNT>`. *Унаследованный* маршрут, который и так разрешается в `<ACCOUNT>`,
  **не** является no-op: точной привязки ещё нет, поэтому фиксация всё равно
  запишет закрепляющую привязку, и `would_change` равно `true`.

### Фиксация — `--expect-state <token>`

```bash
$ claude-acc link --json --path /Users/alice/work/project-a --account work \
    --expect-state 42cfd5972ba543f2f876687273ffc9b737971b0b4589fc342d71cd4b95991f77
{
  "schema_version": 1,
  "ok": true,
  "dry_run": false,
  "changed": true,
  "query_path": "/Users/alice/work/project-a",
  "account": "work",
  "before": { "resolved_account": "default", "source": "standard", "owning_link_path": null },
  "after": { "resolved_account": "work", "source": "linked", "owning_link_path": "/Users/alice/work/project-a" },
  "stored_link_path": "/Users/alice/work/project-a"
}
```

- `after` здесь — **проверенный** маршрут, перечитанный из файла после записи.
- Фиксация, обнаружившая, что точная привязка уже на месте, — это **успешный
  no-op**: `changed: false`, файл не переписывается, `before`/`after` равны.

### Исходы и что каждый означает для файла

Фиксация `link --json` завершается ровно в одном из четырёх состояний, и
различие важно, потому что они оставляют файл не в одном и том же месте:

- **Определённый отказ до фиксации** — любой `error.code` из списка ниже, *кроме*
  `POSTCONDITION_FAILED`. Отказ принимается до какой-либо записи, поэтому файл
  байт-в-байт неизменен. Это те случаи, что ничего не пишут.
- **Успешный no-op** (`ok: true`, `changed: false`) — точная привязка уже была на
  месте; файл не переписывается, `before`/`after` равны.
- **Успешная зафиксированная мутация** (`ok: true`, `changed: true`) — точная
  привязка записана и перепроверена; `after` — это маршрут, перечитанный из
  файла.
- **Неопределённый исход после фиксации** (`POSTCONDITION_FAILED`) — запись была
  предпринята, и файл **мог измениться**, но маршрутизация не перепроверилась как
  ожидалось. Это тоже конверт отказа, но, в отличие от остальных, он **не**
  гарантирует, что ничего не записано; он никогда не сообщается как "не
  изменилось" и **не** откатывается автоматически.

Любой отказ представляет собой конверт операционной ошибки (`ok: false`,
выход 1). Ветвитесь по `error.code`, а не по `message`:

- `STATE_CHANGED` — токен `--expect-state` больше не совпадает; подтверждённое
  пользователем состояние сдвинулось. В `details` лежит текущий маршрут
  `before`. Сделайте предпросмотр заново и решайте снова.
- `AMBIGUOUS_LINK` — маршрутизация для каталога уже неоднозначна (две
  эквивалентные хранимые привязки называют разные аккаунты). Отказ, а не тихое
  "исцеление"; файл остаётся ровно таким, как был.
- `ACCOUNT_NOT_FOUND` / `ACCOUNT_NAME_INVALID` — аккаунт не является управляемым
  (или стандартным `default`) либо имя аккаунта недопустимо.
- `PATH_NOT_FOUND` / `PATH_NOT_DIRECTORY` — как у `status --json`.
- `PATH_NOT_REPRESENTABLE` — каталог нельзя без потерь сохранить в формате строки
  `dir=account` (например, он содержит перевод строки или пробелы, которые
  парсер обрежет). Файл никогда не портится путём, который он не может
  представить.
- `LINKS_STORE_INVALID` / `LINKS_STORE_UNREADABLE` — файл повреждён или
  нечитаем; повреждённый файл отклоняется, а не переписывается этим путём.
- `CONFIG_STORE_UNREADABLE` — файл конфигурации (где хранится `default=`) или
  список аккаунтов существует, но не удалось прочитать или декодировать.
  В отличие от человекочитаемого пути, который трактует нечитаемый конфиг как
  "нет default", машинный путь включает default в отпечаток и сообщает его как
  часть маршрута, поэтому он отказывает громко, а не фиксирует изменение против
  искажённого маршрута before/after и токена.
- `NOT_INITIALIZED` — у claude-acc ещё нет файла маршрутизации. Эта команда его
  никогда не создаёт (поэтому у dry-run нет побочного эффекта); инициализируйте
  его, выполнив сначала любую другую команду claude-acc.
- `LINKS_STORE_LOCKED` — другой кооперирующий писатель удерживает блокировку
  маршрутизации; повторите попытку.
- `LINKS_STORE_WRITE_FAILED` — сама запись не удалась; файл не изменён.
- `POSTCONDITION_FAILED` — привязка записана, но маршрутизация не перепроверяется
  как ожидалось. Исход **неопределён**: файл мог измениться, поэтому это никогда
  не сообщается как "не изменилось" и **не** откатывается автоматически.
  Перечитайте маршрутизацию (`status --json`, `links --json`) и согласуйте
  состояние перед любой повторной попыткой.
- `INVALID_ARGUMENTS` — указан не ровно один из `--dry-run`/`--expect-state` либо
  отсутствует `--path`/`--account`.

### Атомарность, блокировка и кого она связывает

- **Атомарная запись файла.** Файл привязок (и `default=` в конфиге) заменяется
  через временный файл в том же каталоге, fsync и затем rename, поэтому читатель
  всегда видит либо полностью старый, либо полностью новый файл — никогда
  разорванный — а сбой между шагами оставляет прежний файл целым. Это
  безопасность при прерывании процесса, а **не** гарантия устойчивости к потере
  питания самого rename (каталог не fsync-ается).
- **Одна блокировка маршрутизации.** Единственная рекомендательная блокировка ОС
  сериализует всех писателей значимого для маршрутизации состояния *в этом
  бинарнике* — машинную мутацию, человеческие `link`/`unlink` и изменения
  `default`/удаления аккаунта — так что их read-modify-write не могут
  переслоиться. Она снимается автоматически при завершении процесса, поэтому
  упавший держатель не оставляет ничего "застрявшего", и ничего не удаляется по
  возрасту.
- **Она связывает только кооперирующих писателей этого бинарника, и границы
  точны.** *Старый* claude-acc без блокировки, прямое ручное редактирование
  файла привязок или shell-интеграция (`claude-switch.sh`, другой механизм)
  **не** сериализуются ею. Защиты от некооперирующей записи многослойны, и их
  пробелы тоже:
  - Изменение, видимое **до** сравнения expected-state при фиксации, либо
    попавшее **между** этим сравнением и финальной записью, ловится — проверкой
    токена и вторым консервативным перечитыванием непосредственно перед заменой
    — и отклоняется с `STATE_CHANGED`. Чужая запись выживает.
  - Некооперирующая запись в оставшемся окне — **после** этого последнего
    перечитывания и **до** атомарного rename — заранее не обнаруживается, и эта
    запись молча перезаписывается. Перепроверка после записи всё ещё ловит
    неверный *итоговый* маршрут (`POSTCONDITION_FAILED`), но не может воскресить
    затёртую параллельную запись. Это окно сужено, а не закрыто.
  - Смена идентичности каталога в файловой системе вне блокировки (смена цели
    reparse/junction) также не сериализуется; токен связывает разрешённый
    маршрут, полный набор точной эквивалентности и собственную разрешённую
    идентичность каталога, чтобы поймать её на момент сравнения — включая
    смену цели, которая расширяет или сужает то, какие хранимые записи попадают
    в класс эквивалентности `<DIR>`, не меняя ни одной хранимой строки, — но не
    внутри этого финального окна.
  - Поскольку токен — это *отпечаток* состояния, изменение типа ABA (значение
    изменилось и было восстановлено тождественно) неотличимо от отсутствия
    изменения.
  - **Операционное предусловие:** потребитель не должен выполнять эту команду
    против файла, который параллельно изменяет другой некооперирующий писатель
    (старый бинарник, shell-интеграция, ручная правка, внешний инструмент).
    Внутри собственных команд этого бинарника блокировка делает это безопасным;
    относительно тех других писателей это ответственность вызывающего, и
    гарантия деградирует до многослойного best-effort выше.

## Версионирование

`schema_version` — отдельная для каждой команды величина, начинающаяся с
`1`. Потребитель должен отказываться работать с `schema_version` ниже
требуемой ("claude-acc нужно обновить") и отказываться работать с более
высокой, чем он понимает ("claude-acc новее, чем ожидает эта сборка") —
никогда не разбирать её тихо "как получится" в любую сторону.
